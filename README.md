# mfind — 쌓인 파일에서 원하는 것만 골라내는 도구

**AX혁신과 자율스터디 3차 미션 · 작은 업무 에이전트 시제품**
제출: 스터디 대시보드 · 산출물: 실행 파일 1개 + 웹 앱 1개 + 소스 전체

---

## 1. 어떤 업무 문제를 풀었나

세 가지가 실제로 매일 시간을 잡아먹는다.

**① 파일을 못 찾는다.** 이름은 기억나는데 어느 폴더에 뒀는지 모른다. 탐색기 검색은
느리고, 찾은 뒤에도 다음에 또 찾는다.

**② 같은 파일이 여기저기 흩어져 있다.** `2026_사업계획_최종.hwp`,
`2026_사업계획_최종_v2.hwp`, `사업계획_진짜최종.hwp` — 이름이 다르니 중복인 줄
모른다. 어느 게 최신인지도 모르고, 디스크만 먹는다.

**③ 자주 쓰는 파일이 우대받지 않는다.** 하루에 열 번 여는 파일과 2년 전에 한 번
연 파일이 검색 결과에서 동등하게 나온다.

①은 [Everything](https://www.voidtools.com/) 이 이미 훌륭하게 푼다. 그래서 ①은
그 접근법을 따르고, **Everything 이 못 하거나 반쪽인 ②·③을 더했다.**

## 2. 만든 것

두 가지 형태로 만들었다. 같은 설계를 두 환경에 옮겨 각각의 한계를 확인하는 것이
이 시제품의 목적 중 하나였다.

| | 네이티브 (`mfind.exe`) | 웹 (`web/app.html`) |
|---|---|---|
| 형태 | 무설치 단일 실행 파일 (약 706 KB) | 단일 HTML, 서버·빌드 없음 |
| 실행 | 더블클릭 → 대화형, 또는 CLI | 브라우저에서 열기 |
| 접근 범위 | 드라이브 전체 (MFT 직접 읽기 가능) | 사용자가 허용한 폴더 |
| 파일 열기 | 가능 (열면서 사용 횟수 +1) | **불가** — 경로 복사·내려받기만 |
| 의존성 | 4개 (`blake3` `serde` `serde_json` `walkdir`) | **0개** |

- **웹 데모** — https://themoka7.github.io/AI_Maestro_Self_03/ (Chrome·Edge)
- **실행 파일** — `Actions` → `CI` → 최신 실행의 `mfind-windows-x64` 아티팩트

```
> 휴가
  1.   12회  8.31   195.3 KB  D:\사진\휴가_2024.jpg          [중복 1]
  2.    -       -   195.3 KB  D:\백업\사진2\IMG_0421.jpg      [중복 1]
  3.    -       -   195.3 KB  E:\정리안된것\vacation-copy.jpg [중복 1]
```

세 파일은 이름에 공통점이 하나도 없다. `[중복 1]` 이 같은 내용임을 말해 준다.
맨 왼쪽 `12회 8.31` 은 사용 빈도다.

## 3. 설계 결정 세 개와 그 근거

시제품에서 진짜 내용은 "무엇을 만들었나" 가 아니라 "왜 그렇게 만들었나" 라고
보고, 판단이 갈렸던 지점만 적는다.

### 3.1 빈도는 누적 카운터가 아니라 반감기 점수로

Everything 에도 `Run Count` 가 있다. 하지만 **Everything 을 경유해서 실행한 파일만**
세고, 단순 누적이라 2년 전에 100번 열었던 파일이 어제 세 번 연 파일을 계속 이긴다.

OS 도 도와주지 않는다. NTFS 에는 파일별 open 카운터가 **없다.**

| 쓸 수 있는 소스 | 얻는 것 | 한계 |
|---|---|---|
| NTFS Last Access Time | 마지막 접근 1건 | Win10 1803+ 기본 비활성, 1시간 granularity |
| USN Journal | 변경(쓰기·이름변경·삭제) 이력 | **읽기는 안 남는다** |
| Prefetch (`.pf`) | 실행 횟수 + 최근 8회 | exe 전용 |
| UserAssist 레지스트리 | 탐색기로 실행한 항목의 횟수 | GUI 실행분만 |
| ETW `Kernel-File` | 실시간 CreateFile 전량 | 관리자 권한, 초당 수천 건의 노이즈 |

그래서 **직접 쌓되, 시간에 따라 감쇠하는 점수를 쓴다.**

```
score(t) = score(last) × 0.5^((t − last) / 반감기) + 1        반감기 기본 30일
```

zoxide 나 Firefox 의 frecency 와 같은 발상이다. 튜닝 지점이 반감기 하나로 줄고,
손대지 않은 항목은 쓰기 없이도 저절로 순위가 낡는다.

그리고 **빈도가 쌓이는 경로를 UX 로 만들었다.** 통계가 의미를 가지려면 "이 도구로
파일을 여는 게 가장 편한 길" 이어야 한다. 대화형 모드에서 검색 후 **번호만 입력하면
열면서 +1** 이 된다.

### 3.2 중복은 전수 해싱이 아니라 3단계 퍼널로

이름 인덱스만으로는 `휴가_2024.jpg` 와 `IMG_0421.jpg` 가 같은 사진인지 알 수 없다.
그런데 전수 해싱은 디스크가 감당하지 못한다. 그래서 좁힌다.

| 단계 | 방법 | 비용 |
|---|---|---|
| 1 | **크기**로 묶는다 | 인덱스에 이미 있으므로 **I/O 0** |
| 2 | 같은 크기 후보만 **앞 16KiB 해시** | 대부분의 오답이 여기서 걸러진다 |
| 3 | 살아남은 것만 **전체 해시** | 실제로 읽는 양은 전체의 극히 일부 |

크기가 다르면 내용도 다르다 — 1단계가 공짜인 근거다. `(경로, 크기, mtime)` 이
그대로면 해시를 재사용한다.

**하드링크를 낭비 용량에서 제외한다.** 이걸 빼먹으면 물리적으로 한 파일인 것을
여러 개로 세서 "중복 500GB" 같은 거짓 보고가 나온다.

### 3.3 웹은 인덱싱을 두 단계로 쪼갠다

처음엔 한 번에 다 했다. D: 에 걸어 보니 **몇 분씩 걸렸다.** 원인은 코드에 있었다 —
파일마다 `getFile()` 왕복을 **동시성 1로 순차** 처리했다. 지연 시간에 묶인 작업을
한 번에 하나씩 던지고 있었다.

여기서 진행률 문제와 만난다. 브라우저 API 는 순회하지 않고 개수를 알려주지 않으므로
**진행률의 분모를 만들 방법이 없다.** 단계를 나눠 둘 다 해결했다.

| | ① 폴더 인덱싱 | ② 크기·시각 읽기 | ③ 중복 찾기 |
|---|---|---|---|
| 하는 일 | 트리 열거 | 파일마다 `getFile()` | 3단계 퍼널 |
| 비용 | 디렉터리당 왕복 1번 | **파일당 왕복 1번** | 후보만 실제로 읽음 |
| 여는 것 | **이름으로 검색** | **크기 정렬·필터**, ③의 전제 | **이름이 달라도 같은 내용** |
| 진행률 | 없음 (발견 개수·처리량) | 진짜 % + 남은 시간 | 단계별 생존 개수 |
| 범위 | 고른 폴더 전체 | 인덱스 전체 | **지금 검색 결과 안에서만** |

①이 끝나면 검색이 바로 되고 총계가 확정된다. ②는 ①이 만든 트리를 재사용하므로
다시 훑지 않는다 — 각 디렉터리 항목이 자식의 연속 범위(`childStart`/`childCount`)를
들고 있어 이름으로 자식을 O(자식 수)에 찾는다. 핸들을 100만 개 보관하지 않아도 되고
큰 맵도 없다.

①·② 모두 요청을 동시에 여러 개 던진다(`동시 요청`, 기본 32). 지연 시간에 묶인
작업이라 **동시성이 곧 속도다.**

**②의 진행 표시 — 달까지.** 가장 오래 걸리는 단계라 %만 보여 주면 감이 없다.
파일 총 개수를 달까지의 거리(384,400 km)로 환산해 🌍 → 🚀 → 🌕 로 보여 준다.
([moon_mission](https://themoka7.github.io/dev-tools/tools/etc/moon_mission.html) 에서
가져온 발상.) 환산이 일관되므로 **장식이 아니다** — 파일 하나 = `384400 / 전체` km,
속도 = `파일초당 × 파일당 km × 3600` 이라 `남은 거리 ÷ 속도` 가 실제 남은 시간과
정확히 같다. 같은 수치의 다른 눈금일 뿐이고, 그 등식을 테스트가 검증한다.

## 4. 검증한 것과, 검증하지 못한 것

시제품에서 이 구분이 가장 중요하다고 보고 분리해서 적는다.

### 확인된 것

| 대상 | 방법 | 결과 |
|---|---|---|
| 네이티브 코어 | 단위 테스트 72개 | 통과 (Ubuntu·Windows 양쪽 CI) |
| 정적 검사 | `cargo clippy -D warnings`, `cargo fmt --check` | 무경고 (두 타깃) |
| 웹 2단계 인덱싱 | 가짜 디렉터리 핸들로 실제 실행 | 15개 통과 |
| 릴리스 빌드 | CI 에서 MSVC 빌드 + 아티팩트 업로드 | 성공 |
| 웹 배포 | Pages 워크플로가 자체 점검 통과 후에만 배포 | 게이트 동작 확인 |

웹 자체 점검이 확인하는 것: 경로 재구성, **자식 범위 정합**(한 칸만 어긋나면 엉뚱한
파일에 크기가 붙고 그건 곧 잘못된 중복 보고다), 크기·시각 정확도, 퍼널 1단계 개수,
그리고 위의 `남은 거리 ÷ 속도 = ETA` 등식.

### 확인하지 못한 것 — 쓰기 전에 알아야 할 것

- **`--mft` 백엔드는 컴파일 검증만 됐다.** NTFS MFT 를 USN 열거로 한 번에 읽는
  경로(`DeviceIoControl`, `FindFirstFileW`)를 실제 NTFS 볼륨에서 돌려 보지 못했다.
  개발 환경이 Linux 컨테이너였다. 기본 `walk` 백엔드는 영향이 없다.
- **웹의 실제 처리량을 숫자로 재지 못했다.** 병렬화 전에는 "엄청 느리다" 는 것만
  확인했고, 병렬화 후 D: 규모에서 몇 개/초가 나오는지는 측정 대기 중이다.
  UI 좌측 처리량 판독값이 실측치를 그대로 보여 준다.
- **전역 접근 빈도 수집기가 없다.** 지금 세는 것은 이 도구를 경유한 열기와
  `mfind hit` 호출뿐이다. 탐색기·IDE 로 연 것까지 잡으려면 ETW 상주 수집기가
  필요하고, 그때 작업량의 대부분은 노이즈 필터링이 될 것이다.

## 5. 에이전트로 가려면 무엇이 더 필요한가

**지금 이것은 도구다.** 물어보면 답하지만, 스스로 판단해서 대신 일하지는 않는다.
미션 주제가 "에이전트" 이므로 그 격차를 분명히 적는다.

| 갖춘 것 (에이전트의 전제) | 없는 것 (에이전트의 조건) |
|---|---|
| 상태를 관찰한다 (인덱스·빈도·중복) | **스스로 깨어나지 않는다** — 사람이 눌러야 돈다 |
| 판단 근거가 되는 신호가 있다 (감쇠 점수, 낭비 용량) | **행동하지 않는다** — 정리·이동·삭제를 제안만도 안 한다 |
| 결정이 재현 가능하다 (해시로 확정) | **목표가 없다** — "디스크를 20% 비워라" 같은 것을 받지 못한다 |
| 기계가 읽는 출력이 있다 (`--paths`) | **보고하지 않는다** — 결과를 사람에게 밀어주지 않는다 |

에이전트로 만드는 가장 짧은 경로는 이 순서라고 본다.

1. **상주 + 주기 실행** — 인덱스를 자동으로 갱신하고 새로 생긴 중복을 스스로 찾는다.
   USN Journal 실시간 추적이면 전체 재스캔 없이 변경만 반영할 수 있다.
2. **제안 생성** — "이 3개는 같은 파일이고 2.2MB 를 낭비한다. 가장 최근 것은
   `사업계획_진짜최종.hwp` 다" 까지 만든다. 판단 근거(해시·mtime·빈도)를 함께 낸다.
3. **승인 후 실행** — 사람이 승인하면 정리한다. 되돌릴 수 있게 하고, 삭제는 절대
   기본값으로 두지 않는다. 파일을 지우는 자동화는 틀렸을 때 대가가 크다.
4. **보고** — 주간 요약을 사람이 있는 곳(메일·메신저)으로 밀어준다.

2번까지가 실질적인 가치의 대부분이고, 3번이 위험의 대부분이다.

## 6. 직접 돌려보기

### 웹 — 설치 없음

https://themoka7.github.io/AI_Maestro_Self_03/ 을 Chrome 이나 Edge 로 열고
**① 폴더 선택** 을 누른다. `문서` 나 `사진` 폴더로 시작하는 것을 권한다.

```sh
# 로컬에서 (File System Access API 는 보안 컨텍스트를 요구한다 — file:// 은 안 된다)
python3 web/build.py _site && python3 -m http.server -d _site 8080
```

### 네이티브

```sh
cargo build --release                                   # 현재 플랫폼
cargo build --release --target x86_64-pc-windows-msvc   # 윈도우
cargo build --release --target x86_64-pc-windows-gnu    # 리눅스에서 크로스 (mingw-w64)
cargo test && cargo clippy --all-targets -- -D warnings
```

```sh
mfind                                   # 인자 없이 = 대화형 (exe 더블클릭도 여기로)
mfind index D:\ --exclude node_modules  # 인덱스 만들기
mfind index C:\ --mft                   # MFT 직접 읽기 (관리자 권한, 미검증)
mfind search 보고서 --mark-dup          # 중복 표시하며 검색
mfind dup 사진/ --min-size 1mb          # 사진 폴더의 중복만
mfind top                               # 자주 쓰는 파일 순위
mfind open D:\문서\보고서.hwp           # 열면서 빈도 +1
```

`rust-toolchain.toml` 이 컴파일러를 1.98.1 로 고정한다. clippy 는 릴리스마다 새
lint 를 켜므로, 고정하지 않으면 로컬은 통과하는데 CI 가 빨개진다 (실제로 겪었다).

### 웹 자체 점검

```sh
python3 web/build.py _site && cp web/selftest.js _site/
printf '\n<script src="selftest.js"></script>\n' >> _site/index.html
# 브라우저에서 _site/index.html?selftest=1 → 탭 제목이나 콘솔에 결과
```

## 7. 부록

### 질의 문법

Everything 문법의 부분집합 + 몇 가지. 공백으로 나뉜 조각은 AND 로 묶인다.

| 예 | 뜻 |
|---|---|
| `report final` | 이름에 둘 다 (대소문자 무시) |
| `*.rs`, `ma?n.*` | 글롭 |
| `src/main` | 구분자가 있으면 전체 경로로 매칭 |
| `ext:rs,toml` | 확장자 |
| `size:>10mb` | 크기 (kb/mb/gb/tb, 1024 기준) |
| `runcount:>3` | 누적 사용 횟수 |
| `dup:` | 내용이 같은 짝이 있는 파일만 |
| `file:` / `folder:` | 종류 |
| `!draft` | 부정 |
| `"my report"` | 공백 포함 |

### 인덱스 구조

Everything 이 가벼운 이유는 항목당 힙 할당을 만들지 않는 데 있다. 여기도 같다.

- 이름은 전부 하나의 바이트 아레나에 눌러 담는다
- 각 항목은 고정 36바이트 레코드:
  `(name_off, name_len, flags, parent, size, mtime, file_id)`
- 부모는 항목 배열 자신에 대한 인덱스다. 경로는 저장하지 않고 부모 사슬로 만든다
- 직렬화는 손으로 쓴 바이너리다 — 백만 항목에 JSON 은 감당이 안 된다

100만 파일이면 레코드 36MB + 이름 블롭이다. 웹에서도 같은 발상으로 평행
TypedArray 를 쓴다 (항목당 객체를 만들면 GC 가 무너진다).

검색은 2단계다. 1회차는 경로를 조립하지 않고 이름·크기만 본다 — 100만 항목에서 매번
부모 사슬을 거슬러 문자열을 만들면 그게 검색 시간의 전부가 된다.

### 저장 위치

| | 네이티브 | 웹 |
|---|---|---|
| 위치 | `%LOCALAPPDATA%\mfind\` (`MFIND_DATA_DIR` 로 변경) | 이 출처의 IndexedDB |
| 파일 | `index.bin`, `usage.json`, `hashes.json` | 같은 세 가지 |
| 쓰기 | 임시 파일에 쓴 뒤 rename — 도중에 죽어도 기존 파일은 온전 | — |

### 웹에서 안 되는 것

- **Chrome·Edge 만.** `showDirectoryPicker` 가 Firefox·Safari 에 없다.
- **파일을 열 수 없다.** 브라우저가 네이티브 앱을 띄우지 못한다. 그래서 `경로 복사`와
  `내려받기`만 제공하고, 이 두 동작을 사용 1회로 센다. 내려받기는 뷰어가 중개하며
  허용된 확장자에만 뜬다 — `.hwp` `.rs` 는 목록 밖이라 `경로 복사`만 남는다.
- **드라이브 루트를 고르면 그 아래가 다 열린다.** Chromium 의 차단 목록에 드라이브
  루트는 없고, 검사는 피커에서 고른 경로에만 적용된다. 그래서 기본 제외 목록에
  `AppData`·`Windows`·`Program Files` 를 넣어 뒀다 — 안 그러면 이 페이지가 브라우저
  프로필과 `.ssh` 키까지 읽을 수 있다.
- 모든 처리는 브라우저 안에서만 일어난다. 파일 내용도 경로도 어디로도 전송되지 않는다.

```
src/frecency.rs   반감기 점수 저장소

src/scan/walk.rs  이식 가능한 디렉터리 스캐너 (기본)
src/scan/win_mft.rs  NTFS MFT 일괄 읽기 (미검증)
src/usn.rs        USN_RECORD_V2 파서 — OS 호출을 분리해 어디서나 테스트된다
src/repl.rs       대화형 모드
web/app.html      웹 앱 전체 (의존성 0)
web/build.py      아티팩트용 조각을 단독 문서로 감싼다
web/selftest.js   가짜 핸들로 2단계 인덱싱을 실제 검증
```
