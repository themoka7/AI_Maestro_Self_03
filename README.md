# 기출문제 처리기

**문제지를 올려 두면, 올린 그 순간 알아서 문항으로 쪼개 놓는다.**
사람이 스크립트를 돌리지 않는다.

**AX혁신과 자율스터디 3차 미션 · 작은 업무 에이전트 시제품**

```
exam/papers/ 에 PDF·HWP 업로드
        ↓  GitHub Actions 가 그 업로드를 신호로 깨어난다
   파서 점검 → 문항 추출 → 열람용 HTML → 결과 확인 → 보고 → 레포에 되커밋
        ↓
exam/out/questions.json   기계가 읽는 구조화 데이터
exam/out/index.html       사람이 보는 페이지 (검색·교시 필터)
Actions 실행 요약          회차별 문항 수와 경고가 담긴 표
```

---

## 1. 어떤 업무 문제를 풀었나

기술사 준비든 출제 분석이든, **기출문제는 PDF 뭉치로 온다.** 30개 회차면 PDF 30개다.
"WBS 가 몇 회에 나왔지" 를 알려면 30개를 하나씩 열어 눈으로 훑어야 한다.
Ctrl+F 는 파일 하나 안에서만 듣고, 그마저도 문항 경계를 모르니 검색어가 안내문에
걸리는지 문항에 걸리는지 구분이 안 된다.

필요한 것은 **문항 단위로 쪼개진 데이터**다. 그러면 회차 횡단 검색도, 출제 빈도
집계도, 교시별 필터도 전부 따라온다.

그런데 그 변환을 사람이 매번 돌리게 만들면 결국 안 한다. **파일을 올려 두는 것
말고는 아무것도 안 해도 되어야 한다.**

## 2. 업로드하면 처리된다

### 브라우저에서 (설치 없음)

1. 이 레포의 [`exam/papers/`](exam/papers/) 폴더를 연다
2. **`Add file` → `Upload files`**
3. 문제지 PDF·HWP 를 끌어다 놓고 **`Commit changes`**
4. **`Actions` 탭 → `기출문제 처리`** 실행이 저절로 시작된다
5. 실행 페이지 요약에 결과 표가 뜨고, `exam/out/` 에 결과가 되커밋된다

git 을 쓴다면 `exam/papers/` 에 넣고 push 하면 같다.

> **파일명에 `NNN회` 가 들어 있어야** 회차를 인식한다. `(YYYY년)` 이 있으면
> 시행연도까지 표기된다.
>
> ```
> 제110회 정보관리기술사(2016년).pdf
> ★제139회 정보관리기술사 문제지.pdf
> 제116회 정보관리기술사(2018년).hwp
> ```

### 결과는 실행 페이지에서 바로 읽는다

로그를 뒤지게 하지 않는다. 실행 요약에 이런 표가 쓰인다.

| 회차 | 시행 | 1교시 | 논술형(교시별) | 합계 | 상태 |
|---|---|---|---|---|---|
| 110회 | 2016 | 13 | 6 · 6 · 6 | 31 | 정상 |
| 139회 (추정) | — | 12 | 6 · 6 | 24 | ⚠ 1교시 12문항, 논술형 2개 교시 |

`(추정)` 은 문제지에 교시 번호가 없어 수록 순서로 본 회차다.
**확인된 것과 추정한 것을 섞지 않는다.**

## 3. 나오는 것

`questions.json` — 회차를 키로 하는 구조. 회차 횡단 검색·집계의 입력이다.

```json
{ "papers": { "139": {
    "round": 139, "year": null, "source": "★제139회 ....pdf",
    "gyosi_estimated": true,
    "period1": [[1, "WBS(Work Breakdown Structure) 작성방법"]],
    "essay": [{ "gyosi": 2, "items": [
        { "no": 1, "stem": "AI 리스크에 대하여 다음을 설명하시오.",
          "subs": [["가", "AI 리스크 개념"], ["나", "AI 보안 리스크"]] },
        { "no": 4, "stem": "...", "subs": [], "spec": "학점(Grade) 처리 모듈 ..." }
    ]}]
}}}
```

`index.html` — 검색과 교시 필터가 있는 열람용 페이지. 휴대폰 폭에서 가로 스크롤이
생기지 않는다.

## 4. 설계 결정과 그 근거

### 4.1 트리거를 업로드에 걸었다

"버튼을 누르면 처리" 로 만들면 결국 안 누른다. 사람이 이미 하는 행동(파일을 올림)이
곧 신호가 되어야 한다. 그래서 `exam/papers/**` 에 대한 push 가 트리거다 —
브라우저 업로드도 push 를 만들므로 **git 없이도 같은 경로로 동작한다.**

연달아 올리면 `concurrency` 로 마지막 것만 처리한다. 중간 결과를 커밋할 이유가 없다.

### 4.2 원본은 절대 건드리지 않는다

읽고, 구조화하고, **새 파일로 내놓는 것까지**가 범위다. 문제지를 고치거나 지우지
않는다. 입력을 건드리는 자동화는 틀렸을 때 되돌릴 수 없다.

### 4.3 문제지 양식이 세 가지다

파싱이 단순 정규식으로 안 끝난 지점만 적는다.

| 양식 | 1교시 안내문 | 해당 |
|---|---|---|
| 신 | `※ 총 13문제 중 10문제를 선택하여 설명하시오` | 133회 이후 |
| 구 | `※ 다음 문제 중 10문제를 선택하여 설명하시오` — **문항 수가 없다** | 110~132회 |
| HWP | 안내문이 **표 안에 있어 텍스트에 안 잡힌다** | 116회 |

HWP 는 안내문을 못 찾으므로 **문항 번호가 1로 되돌아가는 지점**을 교시 경계로 쓴다.

### 4.4 교시 번호가 없는 문제지가 있다

110~127회는 헤더에 `제 N 교시` 가 찍혀 있지만 **128회 이후는 없다.**

쪽 번호가 교시인 줄 알았는데 아니었다 — `2 - 1` 은 **「총 2쪽 중 1쪽」** 이다.
그래서 표기가 없는 회차는 **수록 순서를 교시 순서로 본다.** 근거는 표기가 있는
15개 회차 **전부에서 교시 번호가 수록 순서와 일치**한다는 것이고, 추정한 회차는
`gyosi_estimated: true` 로 남겨 결과물에도 `추정` 이 붙는다.

### 4.5 별지가 엉뚱한 문항에 붙는다

문제 하나가 `[명세]` 별지를 참조하는데 그 별지는 **다른 쪽에 인쇄**되어 있다.
순서대로 읽으면 마지막 문항 꼬리에 붙는다. 그래서 별지를 따로 떼어 **`아래 명세` 를
참조하는 문항에 연결**한다. 다음 교시 안내문이 6번 문항에 붙는 것도 같은 이유로 잘라낸다.

## 5. 검증한 것과, 검증하지 못한 것

### 확인된 것

| 대상 | 방법 | 결과 |
|---|---|---|
| 파서 | 합성 문제지(두 양식)로 파싱 검증 | 18개 점검 통과 |
| 파이프라인 | 워크플로가 push 로 깨어나 결과를 되커밋 | 실행 확인 |
| 결과물 온전성 | doctype·charset·viewport 를 커밋 전에 확인 | 게이트 동작 |
| 실제 문제지 | 28개 회차(110~139회, 112·115회 미보유) | **868문항** 경고 없이 추출 |

파서 점검(`exam/tools/selftest.py`)이 보는 것: 문항 경계, 교시 분리, **안내문·쪽번호가
문항에 안 섞이는지**, **별지가 참조 문항에 붙는지**, 파일명에서 회차·연도를 읽는 규칙.
문제지를 레포에 담지 않고도 파서가 조용히 망가지는 것을 막으려고, 추출 **전에** 돌린다.

### 확인하지 못한 것

- **이 레포에는 문제지가 커밋되어 있지 않다.** 저작권이 있는 자료라 담지 않았다.
  그래서 지금 `questions.json` 은 비어 있고, 위 868문항은 로컬에서 확인한 수치다.
  올리면 그때부터 채워진다.
- **스캔 이미지 PDF 는 처리하지 못한다.** 텍스트가 500자 미만이면 그렇게 판단하고
  그 파일만 실패로 알린다 — OCR 은 붙이지 않았다.
- **회차 횡단 집계는 아직 없다.** `questions.json` 이 그 입력이 되도록 만들어 뒀을 뿐,
  "WBS 가 몇 회에 나왔나" 를 세는 쪽은 다음 단계다.

## 6. 이것이 에이전트에 얼마나 가까운가

같은 레포의 첫 산출물(`mfind`, [문서](docs/mfind.md))은 스스로 **"지금 이것은 도구다"**
라고 적고, 에이전트가 되려면 ① 스스로 깨어나기 ④ 보고하기가 없다고 남겨 두었다.
이 처리기는 그 두 칸을 채운 형태다.

| | mfind | 기출문제 처리기 |
|---|---|---|
| ① 스스로 깨어난다 | ✗ 사람이 눌러야 | **✓ 업로드가 트리거** |
| ② 판단하고 근거를 댄다 | ✓ | ✓ (교시 추정에 근거·표시) |
| ③ 행동한다 | ✗ | **△ 새 파일만 만든다.** 원본은 안 건드린다 |
| ④ 보고한다 | ✗ | **✓ 실행 요약 + 결과 되커밋** |

**③ 을 일부러 비워 뒀다.** 원본을 고치는 자동화는 틀렸을 때 되돌릴 수 없다.
읽고 구조화해 새 파일로 내놓는 데까지가 안전하게 자동화할 수 있는 범위다.

여전히 사람이 하는 일: **문제지를 구해 오는 것**(Q-Net 자료실에서 내려받기),
그리고 **답안**(문항 구조화까지가 범위다).

## 7. 직접 돌려보기

```sh
pip install pypdf pyhwp six olefile      # HWP 를 안 쓰면 pypdf 만으로 충분

python3 exam/tools/selftest.py           # 파서 점검 (문제지 없이 됨)
python3 exam/tools/extract.py            # exam/papers → exam/out/questions.json
python3 exam/tools/render.py             # questions.json → exam/out/index.html
python3 exam/tools/summary.py            # 결과를 마크다운 표로
```

| 옵션 | 뜻 |
|---|---|
| `--papers DIR` | 문제지 위치 (기본 `exam/papers`) |
| `--out FILE` | 결과 경로 |
| `--strict` | 문항 수가 안 맞는 경고가 하나라도 있으면 실패로 처리 |

한 파일이 깨져도 나머지는 처리하고, 실패한 파일은 표준오류로 따로 알린다.

구현 세부는 [`exam/README.md`](exam/README.md) 에 있다.
