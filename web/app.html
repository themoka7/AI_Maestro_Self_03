모든 처리가 이 브라우저 안에서만 일어난다. 파일 내용도 경로도 어디로도 전송되지 않는다. 인덱스·빈도·해시 캐시는 이 페이지 출처의 IndexedDB 에만 남는다 — 디렉터리 핸들은 애초에 IndexedDB 밖으로 나갈 수 없는 객체다.

속도. 인덱싱은 두 단계다. 1단계는 이름만 모으고, 끝나면 검색이 바로 된다. 2단계는 파일마다 따로 읽어야 크기·시각을 알 수 있어(getFile() 왕복이 파일당 한 번) 훨씬 오래 걸린다 — 중복 검사에만 필요하므로 기본은 꺼져 있다. 두 단계 모두 요청을 동시에 여러 개 던진다. 동시 요청을 올리면 빨라지지만 브라우저가 버거워지는 지점이 있으니 32 에서 시작해라. 네이티브 mfind 는 MFT 를 한 덩어리로 읽어서 이 왕복 자체가 없다.

진행률. 1단계에는 %가 없다. 브라우저 API 는 순회하지 않고 개수를 알려주지 않으므로 분모가 존재하지 않는다 — 발견한 개수와 처리량만 보여 준다. 총계가 확정되는 2단계부터 진짜 %와 남은 시간이 나온다.

제약. 브라우저는 네이티브 앱을 띄울 수 없다. 그래서 파일을 여는 대신 경로 복사와 내려받기만 제공하고, 이 두 동작을 사용 1회로 센다. 내려받기는 뷰어가 중개하며 허용된 확장자에만 뜬다 — .hwp 나 .rs 같은 건 목록 밖이라 경로 복사만 남는다. 전체 드라이브를 허용하면 이 페이지가 AppData 안의 브라우저 프로필과 .ssh 키까지 읽을 수 있게 된다 — 기본 제외 목록에 넣어 둔 이유다. 네이티브 mfind 는 MFT 를 직접 읽어 훨씬 빠르고 파일도 연다.
